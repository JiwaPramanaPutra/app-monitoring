## Masalah

Form Tambah/Edit Perangkat di halaman Monitoring punya banyak field yang tidak dipakai kode dan membingungkan saat mengisi perangkat (terutama router):

- `Gateway`, `Serial Number`, `External Device ID`, `Device Capabilities` hanya ada di form; tidak dibaca UI mana pun, dan `serialNumber`/`externalDeviceId`/`capabilities` bahkan tidak ada di model `Device` (dibuang Mongoose di mode Mongo).
- `Management Provider` / `Management URL` tersimpan di model tapi tidak dipakai: modal Management membuka `http://<ip>`, bukan `managementUrl`.
- `Gedung` dan `Lantai` diketik bebas, padahal hierarkinya sudah dibuat di halaman Project & Site (tersedia via `/api/projects`).
- Saat create, `signal` untuk Access Point diisi nilai hardcoded `-68 dBm` — angka karangan yang tampil sebagai data monitoring.
- Widget trafik berjudul hardcoded "Mikrotik — router utama", dan pengguna mengira perangkat bertipe Router otomatis menjadi router trafik. Padahal router trafik adalah konfigurasi per-site di Project & Site (RouterOS API), bukan record perangkat.
- Judul tabel "Daftar Access Point & Switch" tetap sama walau isinya Router/Server.

### Masalah batch 2 — create perangkat belum "langsung jalan"

Target yang dituju: ketika app dipakai publik, user menambah perangkat MikroTik sebagai router trafik site harusnya **satu langkah, langsung tersambung, dan grafik langsung menampilkan data asli** — tanpa perbaikan manual di Project & Site dan tanpa melewati keadaan 0/dummy. Sekarang alurnya gagal diam-diam di banyak titik:

- **Default form bridge dijamin salah untuk api-ssl.** `routerBridge` default `port: 8728` dan `interface: 'ether1'` (`monitoring.component.ts:121`, `:734`). Backend selalu memakai TLS (`backend/server.js:158`), dan pada router yang hanya menyalakan `api-ssl` port api polos 8728 memang mati. Menyimpan dengan default = koneksi pasti putus.
- **Nama interface diketik bebas, bukan dipilih dari router.** `GET /api/router/interfaces` sudah punya data asli beserta `running`/`disabled`/`comment`, tapi mengabaikan `?site=` dan selalu memakai config env (`backend/server.js:348`), sehingga tidak bisa dipakai untuk dropdown per-site. Inilah penyebab `ether2` nyasar ke router site lain.
- **Tidak ada tes koneksi saat simpan.** `saveDevice()` (`monitoring.component.ts:742-826`) menyimpan `routerConfig` lalu selesai. Salah port/kredensial baru ketahuan lewat widget yang diam-diam `0 Kbps`.
- **Widget tidak langsung refresh** setelah bridge tersimpan — `fetchRouterTraffic()` tidak pernah dipanggil, baru ke-refresh interval 2 detik. Dan `:813-815` mengganti `selectedSite` langsung tanpa `selectSite()`, sehingga tabel perangkat dan grafik tidak sinkron.
- **Grafik mulai dari kosong selama ±90 detik.** `selectSite()` me-reset `trafficHistory = []` (`:457`), `MAX_HISTORY = 45` (`:83`) dengan polling 2000 ms (`:165`). Padahal backend sudah menyimpan riwayat (`storage.getTrafficHistory()`, `backend/storage.js:185`) yang tidak pernah dipakai untuk mengisi grafik.
- **Grafik tidak terbaca sehingga terkesan dummy.** `scaleCeil`/`chartYUnit` dihitung (`:322-348`) dan `peakRate`/`avgRate` dihitung (`:312-313`) **tetapi tidak pernah dirender** — hanya `chartBars`, `lastTx`, `lastRx` yang dipakai di template. Tidak ada label skala Y, tidak ada satuan, tidak ada sumbu waktu. (Diverifikasi dengan 12 sample polling: 12 pasang nilai unik, Rx 63 Kbps-771 Kbps — datanya asli, tampilannya yang tidak terbaca.)
- **IP perangkat Router tidak tersinkron dengan `routerConfig.host`.** Bridge hanya menulis `routerConfig` saat create (`:841-848`). Mengubah IP perangkat belakangan tidak ikut memperbarui `routerConfig`, sehingga widget terus menunjuk router lama walaupun tabel perangkat sudah benar.

- Gedung dan Lantai jadi dropdown dinamis dari hierarki site (Project → Site → Gedung → Lantai); Ruangan tetap teks bebas. Perubahan gedung mereset lantai.

- Widget trafik: judul jadi "Router trafik site"; saat site belum dikonfigurasi tampilkan tautan "Atur di Project & Site".
- Judul tabel jadi "Daftar Perangkat".
- Label "Nama Perangkat" jadi **Alias** (memang label tampilan, bukan hostname perangkat).
- **Serial Number dikembalikan dengan benar**: ditambahkan ke model `Device` supaya benar-benar tersimpan, lalu muncul lagi di form Add/Edit.
- **Pesan error koneksi router dibuat jelas**: backend tidak lagi mengirim pesan kosong saat RouterOS API gagal (`Gagal terhubung ke RouterOS API <host>:<port> - <sebab>`), dan widget menampilkan pesan itu di bawah status "Koneksi ke router terputus".
- **Bridge router**: di form Add, untuk tipe Router muncul opsi "Jadikan router trafik site ini" + field API Port / Username / Password / Interface, yang mengisi `routerConfig` site terpilih saat disimpan.
- **Fix koneksi TLS RouterOS**: opsi TLS app sebelumnya hanya mengizinkan cipher ADH (tanpa sertifikat). Router yang api-ssl-nya memakai certificate menolak handshake itu (`TLS alert handshake failure`), sehingga trafik tidak pernah tersambung. Diubah ke `ciphers: 'DEFAULT@SECLEVEL=0'` — tetap kompatibel dengan router lama, dan menerima router ber-sertifikat (terbukti konek ke RouterOS 7.7 dengan ECDHE-RSA-AES256-GCM-SHA384).

### Perbaikan batch 2 — create perangkat = langsung jalan

- **Form bridge benar sejak awal**: default `port` `8729`, dan kolom `interface` menjadi **dropdown berisi interface asli router terpilih** lengkap dengan status link UP/DOWN dan rate live (bersumber dari `GET /api/router/interfaces` yang diperbaiki supaya menerima `?site=`).
- **Tes koneksi saat simpan**: setelah `routerConfig` tersimpan, panggil `/api/router/traffic` sekali — toast hijau bila `connected`, toast merah **memakai pesan `error` dari backend apa adanya** bila gagal. Tidak ada lagi kegagalan diam-diam.
- **Widget langsung segar**: setelah bridge tersimpan, reset buffer dan panggil `fetchRouterTraffic()` seketika (tanpa menunggu interval); bila site berubah gunakan `selectSite()` penuh agar tabel dan grafik sinkron.
- **Grafik langsung terisi dari riwayat**: tambah mode raw `GET /api/router/history?site=..&raw=1&limit=45` (endpoint saat ini selalu meng-agregasi, `backend/server.js:560`), lalu prefill `trafficHistory` saat `selectSite()`.
- **Grafik terbaca**: render label skala Y beserta satuan (`scaleCeil`/`chartYUnit`), legend Puncak/Rata-rata (`peakRate`/`avgRate`), dan rentang waktu di bawah grafik — memakai nilai yang sudah dihitung, tanpa menambah perhitungan baru.
- **IP perangkat Router ↔ `routerConfig.host` sinkron**: saat `ipAddress` perangkat bertipe Router yang menjadi router trafik site diubah, `routerConfig.host` ikut diperbarui setelah konfirmasi.

Yang tidak boleh rusak: simpan/edit perangkat, pemilihan site, fallback status perangkat, dan alur modal lain (detail, management, delete). Untuk batch 2: angka trafik wajib berasal dari RouterOS apa adanya — **tidak boleh disintesis atau diisi angka karangan saat belum tersambung** — dan `Laporan Trafik` beserta export CSV tetap memakai format riwayat yang sama.

### rapikan-form-perangkat/F-27 [P1] closed - Stored router password can never be reused, so saving a Router device is blocked until it is retyped

**File:** frontend/src/app/shared/router-traffic-link.ts:174-181; frontend/src/app/pages/monitoring/monitoring.component.ts:669-688, 703-710, 1177-1184; backend/services/redact.js:12-19
**Found:** 2026-09-25 by /audit independent current (scope: current; lens: quality)
**Why it matters:** The Edit modal promises "biarkan kosong untuk memakai yang tersimpan" (`monitoring.component.html:563`) and Step 19 requires credentials to be optional when the site already stores them. But `GET /api/projects` strips every `routerConfig.password` (`backend/services/redact.js:16`), so the `stored` object the component passes to `bridgeDraftError` can never carry a password. `storedPassword` is therefore always `''` and an empty password field always returns "Isi password RouterOS." (`router-traffic-link.ts:175,179-180`). This fires on the common path: `initRouterBridgeForEdit` auto-enables the bridge for the device that already is the traffic router (host equals device IP) and for any Router device on a site without a traffic router (`monitoring.component.ts:686-687`), so opening Edit and changing only the alias or room is rejected until the router password is retyped or the bridge is unchecked. The unit test that claims to cover the stored case (`router-traffic-link.spec.ts:30-35`) builds a fixture the real API never returns, so `npm test` stays green while the feature's one-step promise is broken.
**Suggested fix:** Make "empty password = reuse stored" a first-class signal instead of comparing against a secret the client cannot see. For example expose a non-secret `hasPassword` marker on the projects payload and let `bridgeDraftError` accept an empty password when it is true, or drop the password requirement in the helper and rely on `preserveRouterPasswords` to keep the stored value, erroring only when the site has neither a stored password nor one supplied. Update the spec test to build the payload shape the API actually produces. This changes shipped validation behavior, so it needs the user's explicit decision.
**Resolution:** Repaired 2026-09-25 (after the F-27 review pass). `stripProjectSecrets` now sets a non-secret `routerConfig.hasPassword` marker before deleting the password, `bridgeDraftError` accepts an empty password when that marker (or a supplied password) is present, and the spec test now builds the payload shape `GET /api/projects` actually returns. Backend tests cover the marker and assert `preserveRouterPasswords` strips it so it is never persisted. Awaiting re-review against a new checkpoint.
